# Módulo `chat`

**Pacote:** `br.edu.webchat.chat`
**Fases:** 4 (conversas), 5 (mensagens), 6 (WebSocket)
**Situação:** Fase 4 (conversas) implementada; mensagens e WebSocket pendentes

Responsável pelas conversas, participantes, mensagens, histórico e comunicação em
tempo real.

> As seções de mensagens e WebSocket descrevem o contrato **planejado** a partir da
> [WEB-CHAT-SPEC.md](../WEB-CHAT-SPEC.md) e devem ser atualizadas junto com o código.

## Escopo

O MVP tem **apenas conversas individuais** — dois participantes. Grupos, envio de
arquivos, edição e exclusão de mensagens, respostas e reações estão fora do escopo.

## Modelo de dados

### `chats` — `V4__create_chats.sql` + `V6__add_direct_key_to_chats.sql`

| Coluna | Tipo | Observações |
| ------ | ---- | ----------- |
| `id` | `BIGINT` | PK, `GENERATED BY DEFAULT AS IDENTITY` |
| `direct_key` | `VARCHAR(40)` | par de usuários, menor id primeiro (ex.: `3:4`); `NOT NULL`, **`UNIQUE`** (`uk_chats_direct_key`) — criada por `V6__add_direct_key_to_chats.sql` |
| `created_at` | `TIMESTAMPTZ` | preenchido no `@PrePersist` |
| `updated_at` | `TIMESTAMPTZ` | atualizado no `@PreUpdate`; ordena a listagem |

### `chat_participants` — `V5__create_chat_participants.sql`

| Coluna | Tipo | Observações |
| ------ | ---- | ----------- |
| `chat_id` | `BIGINT` | FK → `chats.id`, `ON DELETE CASCADE` |
| `user_id` | `BIGINT` | FK → `users.id` |

Restrições:

- **PK composta `(chat_id, user_id)`**: um usuário não participa duas vezes da mesma
  conversa;
- **`chats.direct_key UNIQUE`**: existe uma única conversa por par de usuários, garantido
  pelo banco;
- índice `idx_chat_participants_user_id`, usado pela listagem "minhas conversas";
- apagar uma conversa apaga seus participantes (`ON DELETE CASCADE`); apagar um
  usuário que participa de conversas é bloqueado pela FK.

### `messages` (fase 5, planejado)

| Coluna | Tipo | Observações |
| ------ | ---- | ----------- |
| `id` | BIGINT | PK, identity |
| `chat_id` | BIGINT | FK → `chats.id` |
| `sender_id` | BIGINT | FK → `users.id` |
| `content` | texto | não pode ser vazio |
| `created_at` | timestamptz | preenchido automaticamente |
| `read_at` | timestamptz | nulo enquanto não lida |

Migration prevista: `V7__create_messages.sql`.

## Mapeamento JPA

```text
Chat ──@ManyToMany──> User      (tabela de junção: chat_participants)
```

`Chat.participants` é um `Set<User>` mapeado com `@ManyToMany` + `@JoinTable`.

> **Decisão:** a spec original citava uma entidade `ChatParticipant`. Como
> `chat_participants` só tem as duas chaves, sem nenhuma coluna própria, uma entidade
> separada seria abstração sem ganho. Se a tabela ganhar colunas (ex.: "entrou em",
> "silenciada"), o mapeamento passa a ser uma entidade própria — o schema não muda.

A regra "exatamente dois participantes" é garantida pelo único construtor público,
`new Chat(User, User)`, e pela validação no service; não há API para adicionar ou
remover participantes.

O construtor também calcula o `directKey` com `Chat.directKeyOf(id1, id2)`, que ordena os
ids — `directKeyOf(4, 3)` e `directKeyOf(3, 4)` dão `"3:4"`. O campo é `updatable = false`:
os participantes de uma conversa nunca mudam.

### Por que `direct_key`

A PK de `chat_participants` só impede um usuário repetido *dentro* de uma conversa; ela
não impede duas conversas diferentes para o mesmo par. Sem `direct_key`, duas requisições
simultâneas podiam criar conversas duplicadas. Com a coluna, a unicidade do par passa a
ser uma regra do banco, e a busca da conversa existente vira uma consulta simples por
chave, no lugar de dois joins em `participants`.

Campos avaliados e **não** adicionados nesta fase: `status`/`type` (sem moderação nem
grupos no escopo), `created_by` (pouco uso), estado por participante como arquivar ou
silenciar (fora do MVP). `last_message_at` e prévia da última mensagem serão decididos
na fase 5.

## API REST

| Método | Rota | Sucesso | Erros |
| ------ | ---- | ------- | ----- |
| `GET` | `/api/v1/chats` | `200` | — |
| `POST` | `/api/v1/chats` | `201` + `Location` (criou) / `200` (já existia) | `400`, `404` |
| `GET` | `/api/v1/chats/{chatId}` | `200` | `403`, `404` |
| `GET` | `/api/v1/chats/{chatId}/messages` | fase 5 | |
| `POST` | `/api/v1/chats/{chatId}/messages` | fase 5 | |

Todos exigem autenticação (`401` sem token). Nenhum exige papel específico.

### Iniciar conversa

```http
POST /api/v1/chats
Authorization: Bearer <token>
Content-Type: application/json

{ "participantId": 2 }
```

```json
{
  "id": 1,
  "participants": [
    { "id": 1, "name": "Alexandre", "email": "alexandre@email.com", "status": "OFFLINE" },
    { "id": 2, "name": "Maria", "email": "maria@email.com", "status": "ONLINE" }
  ],
  "createdAt": "2026-09-15T01:17:32.953471Z",
  "updatedAt": "2026-09-15T01:17:32.953471Z"
}
```

- O outro participante é informado por `participantId`; o primeiro é **sempre o usuário
  autenticado**, nunca vem do corpo.
- Se já existe conversa entre os dois (em qualquer ordem), ela é **reaproveitada**:
  resposta `200` com a conversa existente, sem `Location`. Quando cria, `201` com
  `Location: /api/v1/chats/{id}`. Assim o front pode chamar `POST` sempre que o usuário
  clicar em um contato.
- O mesmo vale para requisições **simultâneas**: só uma cria, as outras recebem `200` com
  a conversa criada (ver [concorrência](#concorrência-na-criação)).
- `participants` vem ordenado por `id`. `ParticipantResponse` expõe só `id`, `name`,
  `email` e `status` — sem senha, papel ou datas.

### Listar minhas conversas

```http
GET /api/v1/chats
Authorization: Bearer <token>
```

Lista apenas as conversas de que o usuário autenticado participa, da atividade mais
recente para a mais antiga (`updatedAt desc`, desempate por `id desc`). Na fase 5 o
envio de mensagem atualizará o `updatedAt`, fazendo a conversa subir na lista.

### Consultar conversa

```http
GET /api/v1/chats/1
Authorization: Bearer <token>
```

Devolve a conversa com seus participantes.

## Regras de negócio

| Situação | Resultado |
| -------- | --------- |
| `participantId` ausente ou não positivo | `400` com `fields.participantId` |
| `participantId` igual ao próprio usuário | `400` — `BadRequestException` |
| `participantId` inexistente | `404` — `NotFoundException` |
| Conversa entre os dois já existe | reaproveitada, `200` |
| Outra requisição criou a conversa ao mesmo tempo | reaproveitada, `200` |
| `chatId` inexistente | `404` — `NotFoundException` |
| Usuário não participa da conversa | `403` — `ForbiddenException` |

O 403 vale também para `ADMIN`: o papel não dá acesso a conversas de terceiros (ver
[auth](auth.md#autorização-por-papéis)).

Regras previstas para a fase 5: o remetente de uma mensagem é sempre o usuário
autenticado, só participantes enviam mensagens, e conteúdo vazio ou só com espaços é
rejeitado (400).

## Concorrência na criação

`ChatService.create`:

1. busca a conversa por `findByDirectKey` — se existe, devolve com `created = false`;
2. senão, `saveAndFlush(new Chat(me, other))`;
3. se o `INSERT` violar `uk_chats_direct_key` (outra requisição criou no intervalo), captura
   a `DataIntegrityViolationException`, busca de novo por `findByDirectKey` e devolve a
   conversa com `created = false`;
4. se a nova busca não encontrar nada, a violação era outra (ex.: FK de usuário removido) e
   a exceção é propagada.

**`create` não é `@Transactional` de propósito.** Dentro de uma transação, a violação de
constraint a marca como *rollback-only* e a sessão do Hibernate fica inutilizável, então a
nova busca do passo 3 não poderia acontecer. Sem a anotação, cada chamada de repository
roda na própria transação: o `saveAndFlush` falha e é revertido sozinho, e a busca seguinte
abre uma transação limpa. Nenhuma escrita parcial é possível — o único `INSERT` é o do
passo 2, e ele é atômico (conversa + participantes).

Verificado contra o PostgreSQL com 10 `POST /chats` simultâneos para o mesmo par (5 de
cada lado): 1 resposta `201`, 9 respostas `200`, uma única linha em `chats`, nenhum `500`.
As violações tratadas aparecem no log como `ERROR` do `SqlExceptionHelper` do Hibernate;
são esperadas.

## Desempenho (RNF03)

| Operação | Consulta | Queries |
| -------- | -------- | ------- |
| Listar conversas | `findAllByParticipantId`: `join fetch c.participants` + subconsulta pelo usuário | 1 |
| Consultar conversa | `findWithParticipantsById`: `@EntityGraph(attributePaths = "participants")` | 1 |
| Procurar conversa existente | `findByDirectKey`: busca pelo índice único + `@EntityGraph(attributePaths = "participants")` | 1 |

Verificado no log SQL do perfil `dev`: listar 3 conversas executa **uma** query de
chats, com os participantes no mesmo join (as outras duas queries da requisição carregam
o usuário autenticado — uma no filtro JWT, outra no service).

A subconsulta existe para que o `join fetch` traga **todos** os participantes; filtrar
direto no `join fetch` por `p.id = :userId` carregaria só o próprio usuário em cada
conversa.

compartilham o mesmo H2 em memória, e uma conversa esquecida faria a FK de
`chat_participants` quebrar o `userRepository.deleteAll()` de outras classes.

## Divisão REST × WebSocket

| REST | WebSocket |
| ---- | --------- |
| Criação e listagem de conversas | Envio de mensagens em tempo real |
| Consulta de histórico | Recebimento de mensagens |
| Operações persistentes | Eventos de chat |

A persistência é sempre responsabilidade do service — tanto o caminho REST quanto o
WebSocket passam por ele, para que não existam dois caminhos de escrita divergentes.
