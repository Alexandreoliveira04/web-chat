# Módulo `chat`

**Pacote:** `br.edu.webchat.chat`
**Fases:** 4 (conversas), 5 (mensagens), 6 (WebSocket)
**Situação:** Fases 4 e 5 implementadas (REST); WebSocket pendente

Responsável pelas conversas, participantes, mensagens, histórico e comunicação em
tempo real.

> A seção de WebSocket descreve o contrato **planejado** a partir da
> [WEB-CHAT-SPEC.md](../WEB-CHAT-SPEC.md) e deve ser atualizada junto com o código.

## Estrutura

```text
chat/
├── controller/   ChatController, MessageController
├── dto/          CreateChatRequest, CreateChatResult, ChatResponse, ParticipantResponse,
│                 SendMessageRequest, MessageResponse, MessageHistoryResponse, MarkAsReadResponse
├── entity/       Chat, Message
```

Previsto para a fase 6: `websocket/`.

## Escopo

O MVP tem **apenas conversas individuais** — dois participantes. Grupos, envio de
arquivos, edição e exclusão de mensagens, respostas e reações estão fora do escopo.

## Modelo de dados

### `chats` — `V4__create_chats.sql` + `V6__add_direct_key_to_chats.sql`

| Coluna | Tipo | Observações |
| ------ | ---- | ----------- |
| `id` | `BIGINT` | PK, `GENERATED BY DEFAULT AS IDENTITY` |
| `direct_key` | `VARCHAR(40)` | par de usuários, menor id primeiro (ex.: `3:4`); `NOT NULL`, **`UNIQUE`** (`uk_chats_direct_key`) |
| `created_at` | `TIMESTAMPTZ` | preenchido no `@PrePersist` |
| `updated_at` | `TIMESTAMPTZ` | última atividade: atualizado a cada mensagem enviada; ordena a listagem |

### `chat_participants` — `V5__create_chat_participants.sql`

| Coluna | Tipo | Observações |
| ------ | ---- | ----------- |
| `chat_id` | `BIGINT` | FK → `chats.id`, `ON DELETE CASCADE` |
| `user_id` | `BIGINT` | FK → `users.id` |

### `messages` — `V7__create_messages.sql`

| Coluna | Tipo | Observações |
| ------ | ---- | ----------- |
| `id` | `BIGINT` | PK, identity; crescente, por isso também serve de ordem cronológica e de cursor |
| `chat_id` | `BIGINT` | FK → `chats.id`, `ON DELETE CASCADE` |
| `sender_id` | `BIGINT` | FK → `users.id` |
| `content` | `VARCHAR(2000)` | `NOT NULL`, `CHECK (length(trim(content)) > 0)` |
| `created_at` | `TIMESTAMPTZ` | preenchido no `@PrePersist` |
| `read_at` | `TIMESTAMPTZ` | nulo enquanto o destinatário não marcar como lida |

Restrições e índices:

- **PK composta `(chat_id, user_id)`** em `chat_participants`: um usuário não participa duas
  vezes da mesma conversa;
- **`chats.direct_key UNIQUE`**: uma única conversa por par de usuários;
- **`ck_messages_content_not_blank`**: o banco também recusa conteúdo vazio ou só com
  espaços, além da validação da API;
- `idx_chat_participants_user_id`: listagem "minhas conversas";
- `idx_messages_chat_id_id` em `(chat_id, id)`: histórico por cursor e última mensagem de
  cada conversa;
- apagar uma conversa apaga participantes e mensagens (`ON DELETE CASCADE`); apagar um
  usuário que participa de conversas ou enviou mensagens é bloqueado pelas FKs.

## Mapeamento JPA

```text
Chat ──@ManyToMany──> User      (tabela de junção: chat_participants)
Message ──@ManyToOne(LAZY)──> Chat
Message ──@ManyToOne(LAZY)──> User   (sender)
```

`Chat.participants` é um `Set<User>` mapeado com `@ManyToMany` + `@JoinTable`.

> **Decisão:** a spec original citava uma entidade `ChatParticipant`. Como
> `chat_participants` só tem as duas chaves, sem nenhuma coluna própria, uma entidade
> separada seria abstração sem ganho. Se a tabela ganhar colunas (ex.: "entrou em",
> "silenciada"), o mapeamento passa a ser uma entidade própria — o schema não muda.

A regra "exatamente dois participantes" é garantida pelo único construtor público,
`new Chat(User, User)`, e pela validação no service; não há API para adicionar ou
remover participantes. O construtor também calcula o `directKey` com
`Chat.directKeyOf(id1, id2)`, que ordena os ids (`directKeyOf(4, 3)` = `"3:4"`).

`Message` não tem setters: conteúdo, conversa e remetente são `updatable = false` (edição
está fora do escopo). O único campo que muda é `read_at`, e só por `update` em lote no
repository. As associações são `LAZY`; `MessageResponse` usa apenas `getChat().getId()` e
`getSender().getId()`, que o Hibernate resolve pela FK sem carregar a conversa ou o usuário.

### Por que `direct_key`

A PK de `chat_participants` só impede um usuário repetido *dentro* de uma conversa; ela
não impede duas conversas diferentes para o mesmo par. Com `direct_key UNIQUE`, a
unicidade do par passa a ser uma regra do banco, e a busca da conversa existente vira uma
consulta simples por chave.

Campos avaliados e **não** adicionados: `status`/`type` (sem moderação nem grupos no
escopo), `created_by` (pouco uso), estado por participante como arquivar ou silenciar
(fora do MVP), `last_message_at`/`last_message_preview` denormalizados (ver
[listagem](#listar-minhas-conversas)).

## API REST

| Método | Rota | Sucesso | Erros |
| ------ | ---- | ------- | ----- |
| `GET` | `/api/v1/chats` | `200` | — |
| `POST` | `/api/v1/chats` | `201` + `Location` (criou) / `200` (já existia) | `400`, `404` |
| `GET` | `/api/v1/chats/{chatId}` | `200` | `403`, `404` |
| `GET` | `/api/v1/chats/{chatId}/messages?before=&size=` | `200` | `400`, `403`, `404` |
| `POST` | `/api/v1/chats/{chatId}/messages` | `201` | `400`, `403`, `404` |
| `PATCH` | `/api/v1/chats/{chatId}/messages/read` | `200` | `403`, `404` |

Todos exigem autenticação (`401` sem token). Nenhum exige papel específico, e todos que
recebem `chatId` exigem que o usuário **participe** da conversa — inclusive `ADMIN`.

### Formato da conversa (`ChatResponse`)

```json
{
  "id": 1,
  "participants": [
    { "id": 1, "name": "Alexandre", "email": "alexandre@email.com", "status": "OFFLINE" },
    { "id": 2, "name": "Maria", "email": "maria@email.com", "status": "ONLINE" }
  ],
  "lastMessage": {
    "id": 42,
    "chatId": 1,
    "senderId": 2,
    "content": "tudo sim!",
    "createdAt": "2026-09-15T01:45:20.398334Z",
    "readAt": null
  },
  "unreadCount": 3,
  "createdAt": "2026-09-15T01:17:32.953471Z",
  "updatedAt": "2026-09-15T01:45:20.401122Z"
}
```

- `participants` vem ordenado por `id` e expõe só `id`, `name`, `email` e `status`.
- `lastMessage` é `null` em conversa sem mensagens.
- `unreadCount` conta as mensagens **do outro participante** com `readAt` nulo — é
  relativo a quem pergunta.

### Iniciar conversa

```http
POST /api/v1/chats
Authorization: Bearer <token>
Content-Type: application/json

{ "participantId": 2 }
```

- O outro participante é informado por `participantId`; o primeiro é **sempre o usuário
  autenticado**, nunca vem do corpo.
- Se já existe conversa entre os dois (em qualquer ordem), ela é **reaproveitada**:
  `200` com a conversa existente (incluindo `lastMessage` e `unreadCount`), sem
  `Location`. Quando cria, `201` com `Location: /api/v1/chats/{id}`. Assim o front chama
  `POST` sempre que o usuário clica em um contato.
- O mesmo vale para requisições **simultâneas**: só uma cria, as outras recebem `200`
  (ver [concorrência](#concorrência-na-criação-de-conversa)).

### Listar minhas conversas

```http
GET /api/v1/chats
Authorization: Bearer <token>
```

Lista apenas as conversas de que o usuário participa, da atividade mais recente para a mais
antiga (`updatedAt desc`, desempate por `id desc`). Enviar uma mensagem atualiza o
`updatedAt` da conversa, que sobe para o topo.

`lastMessage` e `unreadCount` são **calculados na consulta**, sem colunas denormalizadas em
`chats`: uma query busca a última mensagem de todas as conversas da página e outra conta as
não lidas agrupadas por conversa (ver [desempenho](#desempenho-rnf03)). Assim há uma única
fonte de verdade — a tabela `messages`.

### Consultar conversa

```http
GET /api/v1/chats/1
Authorization: Bearer <token>
```

Mesmo formato de um item da listagem.

### Enviar mensagem

```http
POST /api/v1/chats/1/messages
Authorization: Bearer <token>
Content-Type: application/json

{ "content": "oi Maria" }
```

```json
{
  "id": 42,
  "chatId": 1,
  "senderId": 1,
  "content": "oi Maria",
  "createdAt": "2026-09-15T01:45:20.398334Z",
  "readAt": null
}
```

- O remetente é **sempre o usuário autenticado**; o corpo só tem `content`.
- `content` é obrigatório, não pode ser só espaços e tem no máximo 2000 caracteres.
- Espaços e quebras de linha **nas pontas** são removidos (`strip`) antes de gravar; os do
  meio são preservados.
- O envio atualiza `chats.updated_at` na mesma transação.
- Resposta `201` sem `Location`: não existe rota para consultar uma mensagem isolada.

### Histórico (paginação por cursor)

```http
GET /api/v1/chats/1/messages?size=50
GET /api/v1/chats/1/messages?before=958&size=50
Authorization: Bearer <token>
```

```json
{
  "messages": [ { "id": 958, "...": "..." }, { "id": 959 }, { "id": 1007 } ],
  "hasMore": true,
  "nextBefore": 958
}
```

| Parâmetro | Padrão | Regra |
| --------- | ------ | ----- |
| `size` | `50` | entre 1 e 100 |
| `before` | ausente | id positivo; traz mensagens com `id < before` |

- Sem `before`, traz as `size` mensagens **mais recentes**. Com `before`, as `size`
  imediatamente anteriores ao cursor.
- `messages` vem sempre em **ordem cronológica** (mais antiga primeiro), pronta para exibir.
- `hasMore` indica se existem mensagens mais antigas; `nextBefore` é o valor a mandar em
  `before` para buscá-las (o id da primeira mensagem da página), ou `null` na última página.
- O service busca `size + 1` registros para saber se há mais sem executar um `count`.

> **Decisão: cursor em vez de `page`/`size`.** Com paginação por offset, cada mensagem nova
> desloca as páginas: ao rolar para cima, o usuário veria mensagens repetidas. Com o cursor
> por id, as páginas antigas não mudam quando chegam mensagens novas. Coberto por
> `MessageIntegrationTest.historicoDevePaginarPorCursorSemRepetirMensagens`.

### Marcar como lidas

```http
PATCH /api/v1/chats/1/messages/read
Authorization: Bearer <token>
```

```json
{ "markedAsRead": 3 }
```

Preenche `read_at` de todas as mensagens **recebidas** (enviadas pelo outro participante)
ainda não lidas, com um único `update` em lote. Mensagens do próprio usuário nunca são
afetadas. Chamar de novo devolve `0` — a operação é idempotente.

> **Decisão: endpoint explícito.** O front chama ao abrir a conversa. O `GET` do histórico
> continua sem efeito colateral, o que permite, por exemplo, pré-carregar mensagens sem
> marcá-las como lidas.

## Regras de negócio

| Situação | Resultado |
| -------- | --------- |
| `participantId` ausente ou não positivo | `400` com `fields.participantId` |
| `participantId` igual ao próprio usuário | `400` — `BadRequestException` |
| `participantId` inexistente | `404` — `NotFoundException` |
| Conversa entre os dois já existe (ou foi criada ao mesmo tempo) | reaproveitada, `200` |
| `chatId` inexistente | `404` — `NotFoundException` |
| Usuário não participa da conversa (qualquer endpoint com `chatId`) | `403` — `ForbiddenException` |
| `content` ausente, em branco ou com mais de 2000 caracteres | `400` com `fields.content` |
| `size` fora de 1–100 ou `before` não positivo | `400` com `fields.size` / `fields.before` |
| `before` não numérico | `400` |

O 403 vale também para `ADMIN`: o papel não dá acesso a conversas de terceiros (ver
[auth](auth.md#autorização-por-papéis)).

`MessageService` reaproveita de `ChatService` a busca do usuário autenticado e a checagem
"conversa existe e eu participo" (`findAuthenticatedUser` e `findParticipantChat`, métodos
de visibilidade de pacote), para que a regra de acesso fique em um único lugar.

## Concorrência na criação de conversa

`ChatService.create`:

1. busca a conversa por `findByDirectKey` — se existe, devolve com `created = false`;
2. senão, `saveAndFlush(new Chat(me, other))`;
3. se o `INSERT` violar `uk_chats_direct_key` (outra requisição criou no intervalo), captura
   a `DataIntegrityViolationException`, busca de novo por `findByDirectKey` e devolve a
   conversa com `created = false`;
4. se a nova busca não encontrar nada, a violação era outra (ex.: FK de usuário removido) e
   a exceção é propagada.

**`create` não é `@Transactional` de propósito.** Dentro de uma transação, a violação de
constraint a marca como *rollback-only* e a sessão do Hibernate fica inutilizável, então a
nova busca do passo 3 não poderia acontecer. Sem a anotação, cada chamada de repository
roda na própria transação: o `saveAndFlush` falha e é revertido sozinho, e a busca seguinte
abre uma transação limpa. Nenhuma escrita parcial é possível — o único `INSERT` é o do
passo 2, e ele é atômico (conversa + participantes).

Verificado contra o PostgreSQL com 10 `POST /chats` simultâneos para o mesmo par (5 de
cada lado): 1 resposta `201`, 9 respostas `200`, uma única linha em `chats`, nenhum `500`.
As violações tratadas aparecem no log como `ERROR` do `SqlExceptionHelper` do Hibernate;
são esperadas.

## Desempenho (RNF03)

| Operação | Consultas | Queries |
| -------- | --------- | ------- |
| Listar conversas | `findAllByParticipantId` (`join fetch participants` + subconsulta) → `findLastMessagesOfChats` (`max(id)` agrupado por conversa) → `countUnreadByChat` (`count` agrupado) | **3**, independente do número de conversas |
| Consultar conversa | `findWithParticipantsById` (`@EntityGraph`) + as mesmas 2 de mensagens | 3 |
| Procurar conversa existente | `findByDirectKey` (índice único + `@EntityGraph`) | 1 |
| Histórico | checagem de participante + `findLatest`/`findBefore` com limite `size + 1` | 2 |
| Enviar | checagem + `INSERT` em `messages` + `UPDATE` de `chats.updated_at` | 3 |
| Marcar como lidas | checagem + um `UPDATE` em lote | 2 |

Somam-se a cada requisição as buscas do usuário autenticado (uma no filtro JWT, outra no
service).

Verificado no log SQL do perfil `dev`: `GET /chats` com 3 conversas executou exatamente as
3 queries acima, sem consultas por conversa.

A subconsulta de `findAllByParticipantId` existe para que o `join fetch` traga **todos** os
participantes; filtrar direto no `join fetch` por `p.id = :userId` carregaria só o próprio
usuário em cada conversa. Pelo mesmo motivo de evitar N+1, `lastMessage` e `unreadCount`
são buscados em lote para a lista inteira, e não conversa a conversa.

## Front (páginas estáticas)

`chat.js` passou a usar a API real (`ChatService` em `api.js`):

- a barra lateral lista os colaboradores, com prévia da última mensagem ("Você: ..." quando
  enviada pelo próprio usuário), contador de não lidas e ordenação por última atividade;
  a busca filtra por nome;
- clicar em um contato chama `POST /chats` (cria ou reaproveita), carrega o histórico e, se
  houver não lidas, chama `PATCH .../read`;
- "Carregar mensagens anteriores" usa `nextBefore`, mantendo a posição da rolagem;
- mensagens enviadas mostram ✓ (enviada) ou ✓✓ (lida, conforme `readAt` no momento em que o
  histórico foi carregado).

**Segurança:** todo conteúdo vindo da API (mensagens, nomes) é inserido com `textContent`,
nunca `innerHTML`. A versão anterior montava a lista de contatos e as mensagens com
`innerHTML`, o que permitiria XSS armazenado a partir de um nome ou mensagem com HTML.
Quebras de linha são exibidas via `white-space: pre-wrap` no CSS.

**Sem tempo real ainda:** mensagens recebidas só aparecem ao reabrir a conversa ou recarregar
a página. A atualização automática entra na fase 6 (WebSocket).

## Divisão REST × WebSocket

| REST | WebSocket |
| ---- | --------- |
| Criação e listagem de conversas | Envio de mensagens em tempo real |
| Consulta de histórico | Recebimento de mensagens |
| Operações persistentes | Eventos de chat |

A persistência é sempre responsabilidade do service — tanto o caminho REST quanto o
WebSocket passam pelo `MessageService`, para que não existam dois caminhos de escrita
divergentes.
